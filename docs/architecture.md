# Architecture

This document describes how rose is built. `docs/spec.md` says what rose is and what "done" means; this file says how each part of the spec is implemented. Live facts (addresses, gas, latencies) are in `docs/verification.md`. Method names below are the engine's ABI (`cargo near build non-reproducible-wasm` writes `target/near/rose_engine/rose_engine_abi.json`).

## Components

| Component | Where | Role |
|---|---|---|
| `rose-engine` | `contracts/engine`, NEAR testnet | Classes, positions, NEP-245 units, accrual ledger, liens, cash ledger, rounds, sealed bids, opening, clearing, settlement, foreign custody and payouts. No upgrade path; the final deployment deletes every access key after init (`deploy-engine.sh --role final --keyless`), staging deployments keep one. |
| `rose-ibe` | `contracts/ibe` | Boneh-Franklin IBE against the NEAR MPC CKD key (ported from Sealwell). Compiled into the engine (host-function backend) and into the browser (`packages/ibe-wasm`, wasm-bindgen). |
| `rose-tusdc` | `contracts/tusdc`, NEAR testnet | NEP-141 Test USDC with a public capped mint. The NEAR cash venue. |
| `RoseVault` | `contracts/evm`, Base Sepolia | Immutable custody of Sablier streams and Base USDC, releases funds only against EIP-712 authorizations signed by the engine's MPC-derived key. |
| `TestUSDC`, `DemoToken`, `DemoStreamFaucet` | `contracts/evm`, Base Sepolia | Demo funds and "mint me a demo vesting position". |
| Solana vault | Solana devnet | Ed25519 address derived by the MPC for the engine (path `vault/sol`); holds Streamflow streams and SPL tokens. `gas/sol` pays fees of every engine-built transaction. |
| `mock-mpc` | `contracts/mock-mpc` (tests only) | MPC stand-in of the NEAR sandbox integration tests: derives keys from a fixed test seed and signs what it is asked to sign (secp256k1 and Ed25519), signs the ForeignTx payload hash a test registered for an exact request, and replays recorded real responses only for the very payload or transaction they were recorded for. Like the live contract it refuses ECDSA payloads at or above the secp256k1 group order. It answers in the same block, so it never models a yield timeout or a late second response: the engine's handling of those is covered by the mocked-VM unit tests. Never deployed. |
| `@rose/sdk` | `packages/sdk` | TypeScript bindings, chain adapters, unlock math and the clearing reference used by the "Verify" panel. |
| Web | `apps/web`, Vercel | Landing, app, docs, status. Reads chains directly. `/api/faucet` is a demo convenience, not part of the protocol. |
| Scripts | `scripts` | Deployment (`deploy-base.sh`, `deploy-engine.sh` with its keyless path, `derive-vault-signer.sh`, `rehearse-keyless.sh`, `evm-keystore.ts`), the demo seed and its live proofs (`seed.ts`, `e2e-live.ts`, `demo-manifest.ts` for the guided demo), real-testnet end-to-end runs (`e2e-base-tender.sh`, `e2e-solana-stream.mjs`), the IBE wrapper they share (`ibe.mjs`) and the generator of the web3.js message vectors (`solana-vectors.ts`), recorded in `deployments/`. |

|---|---|---|

No upgrade, migrate, delete or generic call method. |
| `math.rs`, `unlock.rs`, `clearing/`, `ledger.rs` | none | Pure modules (no NEAR dependency): fixed-point arithmetic, the Sablier and Streamflow unlock functions, the Tender and uniform-price clearing, the accrual ledger. Property-tested natively. |

Voluntary receipts check the receiver's NEP-145 capacity; engine-owed credits never do. A `mt_transfer_call` sender cannot withdraw its storage until the resolver ran. `distribute_units` takes at most 30 receivers (`get_limits().max_distribution_receivers`): NEAR caps the logs of one call at 16,384 bytes in total, and 30 is the most whose registration and NEP-245 events fit with 64-character ids. |

## Engine state

All amounts are integers. Token amounts are base units of the token. Cash amounts are base units of the round's cash token (6 decimals). Fractions are fixed point with 1e18 precision, rounded down.

- `config`: MPC account and domain ids (sign secp256k1, sign Ed25519, CKD, ForeignTx), CKD master public key, fee recipient, NEAR cash token, accepted Base cash tokens, RoseVault address and its chain id (the EIP-712 domain), canonical Sablier Lockup address, Streamflow program id, default key timeout and reveal window, derived foreign addresses (`vault/base`, `vault/sol`, `gas/sol`), filled once by the permissionless `bootstrap` that reads `derived_public_key` from the MPC contract.
- `classes`: `class_id -> Class { chain, token, decimals, schedule, positions, total_units, created_at }`. `class_id` is the hex SHA-256 of the borsh-encoded `(chain, token, decimals, normalized schedule)`, so the same economic position always maps to the same class.
- `positions`: `position_id -> Position { class_id, source (Base stream or Streamflow metadata pubkey), allocation, depositor, deposited_at, state (Held, Releasing, Released) }`.
- `holdings`: `(holder, class_id) -> Holding { balance, checkpoint, claimable, carry }`, the NEP-245 ledger with accrual accounting (spec 4); the holder is an account or a Tender's retired lot. Every balance change accrues `balance * (f(now) - checkpoint)` into `claimable` first, carrying the fraction below one base unit into the next accrual (`carry`), so a holding's lifetime accrual is the floor of its exact accrual.
- `storage_accounts`: NEP-145 deposits, bytes used and the list of classes held per account (the account record plus one row per class held and per cash venue with a balance, charged at their measured size for a 64-character account id; the class list is what `get_portfolio` reads).
- `cash`: `(account, venue) -> free cash`. Venues: `Near` (tUSDC NEP-141) and `Base { token }` (an ERC-20 held by RoseVault, its address in canonical spelling; every token is credited, only accepted ones can host rounds). `other_cash_venues`: per account, the Base tokens outside the accepted list it holds cash in, charged with the cash row, so `get_cash` lists every balance.
- `rounds`, `bids`, `orders`: `round_id -> Round { kind, class_id, venue, creator, window, max_price, max_buy_quantity, f_ts, phase, key, result, terms, … }`, one sealed order per `(round, bidder, side)`.
- `liens`, `lien_shares`: `lien_id -> LienRecord { class_id, round_id, holder, lien { units, claim_total, delivered, f_start, excess_credited }, released }` and `(lien_id, funder) -> LienShare { claim, claimed }`.
- `account_index`: per account, the unsettled bids, live Advances, liens held and lien shares (what the views cannot scan and what blocks storage withdrawals).
- `price_history`: per class, the clearing price points.
- `events`: the ring buffer of the last 1,024 events with sequence number, block height, timestamp and predecessor; nobody pays for an entry, so its full size is funded at init.
- `custody`: replay keys (`BaseLog { tx_hash, log_index }`, `SolStream { metadata }`, `SolNonce { account, value }`) with their pending or consumed state and the account a pending registration holds, refused deposits, payouts (`Payout { chain, kind, debit, requester, requested_block, sign_requests, status, digest, base signature, solana transaction (raw message, draws, swept, nonce, receipt account, authority, raw signatures) }`) and their per-account lists, Solana deposit records and stream infos (the withdraw accounts from the attested metadata, `end_time`, `engine_withdrawn` = proven payout withdrawals plus what `sync_sol_stream` booked, the one unconfirmed payout drawing on the stream and its amount), the per-class list of Solana positions a payout may draw on (released and fully withdrawn streams pruned), the per-class swept balance (`SolSwept { balance, pending }`), the nonce and receipt accounts held by unsettled durable-nonce actions, positions with a release in flight, the per-account count of custody actions in flight.

### Stored layouts

State is Borsh: an enum is stored as its variant index and a struct as its fields in order. Rules for every type that reaches storage (records, the event ring buffer, storage-key prefixes, the class schedule) or the MPC payload hash:

- An enum only gains variants at the end; a variant is never inserted, reordered or removed. `tests::layout::borsh_enums_only_gain_variants_at_the_end` pins the stored order of every Borsh enum of the engine and fails on anything but an append.
- A struct field, or a variant's fields, never change in a deployed engine. A change that needs one deploys to a new account (the final engine is deployed keyless and never upgraded; a staging engine updated in place with an incompatible layout cannot read what it wrote before, which is how `get_events` failed on `engine-s3`).

## Round state machine

`Scheduled -> Open -> KeyRequested -> Revealing -> Clearing -> Settled | Cancelled`

| Method | Who | Guard | Effect |
|---|---|---|---|
| `create_tender`, `create_exit`, `create_advance` | issuer, anyone, holder | parameters valid (`closes_at` at most 30 days ahead, `key_timeout` 1 minute to 7 days, `reveal_window` 5 minutes to 7 days; a Tender needs the engine bootstrapped); Tender escrow (budget + 30 bps) and Advance units available; 0.05 NEAR attached | Round `Scheduled` or `Open` |
| `place_bid`, `place_ask` | anyone | `opens_at <= now < closes_at`, fewer than 64 orders, one order per side per account; 0.02 NEAR attached | Stores the ciphertext, escrows cash or locks units, takes the bond |
| `cancel_round` | creator | before the first bid and before `closes_at` | `Cancelled`, everything refundable |
| `close` | anyone | `closes_at <= now < closes_at + key_timeout` | Requests the round key from CKD (retries unbounded until the timeout); a round without orders is cancelled instead |
| `on_round_key` (callback) / `submit_key` | MPC / anyone | the round still waits for a key; the key verifies with one pairing check | `Revealing` from `key_received_at`; a late callback after `cancel_no_key` is ignored |
| `cancel_no_key` | anyone | no key by `closes_at + key_timeout`, no key request in flight (250 blocks after the last `close`) | `Cancelled`, everything refundable |
| `open_bid` | anyone | `Revealing` and inside the window | Full FO verification of `(plaintext, sigma)`; the bid becomes opened, or void if it breaks its collateral |
| `clear` | anyone | window over | Unopened bids void and slashed; clearing price and per-bid fills computed and stored; `Settled` or `Cancelled` when nothing crosses |
| `settle_bid` | anyone | `Settled` or `Cancelled` | Applies one bid's result to the ledger (units, cash, refund, bond, storage deposit); idempotent |
| `release_lien` | anyone | the lien's claim is delivered | Returns the encumbered units to the holder |

Settlement is paginated by construction: `clear` computes the result once (at most 64 orders per round), then each bid is settled by its own call, usually by the participant when they claim.

## Foreign custody

- Bootstrap: `bootstrap` asks the MPC contract for `derived_public_key` of `vault/base` (domain 0), `vault/sol` and `gas/sol` (domain 1) in three joined calls and stores the three addresses once; `scripts/derive-vault-signer.sh` computes the same addresses off chain so RoseVault can be deployed with the right signer before the engine exists.
- Base deposits: the holder calls `RoseVault.depositStream` (or the issuer `createStreams`); the app then calls `register_base_deposit(location, fields)` with the holder's registration deposit. The engine rebuilds the `StreamDeposited` log from the fields, computes the ForeignTx payload hash of its own request (`Log` extractor at `Safe`, no `expected_payload_hash`), and in the callback compares the attested hash, then checks the emitter (RoseVault), the canonical lockup, non-cancelability and transferability, builds the class from the attested schedule and decimals, and mints the units from the deposit checkpoint. A genuine log the engine refuses is recorded and returnable to its sender (`return_refused_deposit`). Base cash deposits (`depositCash`) follow the same path through `register_base_cash`.
- Solana deposits: `attribute_sol_deposit` proves the stream sits at the caller's deposit address (`dep/<account>/<class>`), `move_sol_deposit` has the engine sign `transfer_recipient` to the vault, `register_sol_deposit` proves the stream at the vault with ForeignTx `AccountState` and mints the units (spec 7.2). A registration proof showing the stream elsewhere changes nothing; a stream refused at the vault, or registered once, is never attributed again; callbacks re-check the stage and never remove a consumed or pending replay key. Only fee-free, vault-compatible streams with at least one whole token and an `end_time` more than an hour away are accepted.
- Base payouts are pull-based: the engine debits the ledger, asks the MPC for an EIP-712 signature, checks it recovers to the vault address and stores it; anyone submits it to RoseVault (the beneficiary's browser does it). Final once signed, and never refunded: a failed request is retried at once. `executeRelease` forwards Sablier's withdrawal fee from `msg.value`, and the return of a refused stream also sends what third parties withdrew to the vault for it since its deposit (`vestedForwarded` in `ReleaseExecuted`).
- Solana payouts and redeems are two-phase and use two nonce accounts of the claimant, created from its wallet with seeds bound to its NEAR account (`nonce_seed_prefix_of`, then up to 8 characters; the web uses no suffix for the nonce and `r` for the receipt), authority = `vault/sol`, both reserved to the action until it is settled. `claim_sol_tokens` draws on streams the claimant names (each with at most one unconfirmed payout and more than five minutes before its end) and on the class's swept balance, proves both nonce accounts and the token account in one ForeignTx request, then has `vault/sol` and `gas/sol` sign `[AdvanceNonce] + withdraw per stream + TransferChecked(sum) + [AdvanceNonce(receipt)]`; `redeem` builds `[AdvanceNonce] + transfer_recipient + [AdvanceNonce(receipt)]` after the redeemer paid the stream's unwithdrawn unlocked tokens from its claimable. The record stays `Signed` (anyone can broadcast the stored transaction) until `confirm_sol_payout(payout_id, anchor_tx, nonce_data, receipt_data)` / `confirm_sol_redeem(position_id, anchor_tx, nonce_data, receipt_data)` proves the nonce advanced and reads the receipt; no stream takes part. The receipt on the nonce's new value means executed, `Landed` (withdrawals counted, swept reservation paid, release final); the receipt behind it on two proofs 150 blocks apart means not executed, `Failed` with the debit refunded (units re-minted from the burn, paid claimable returned, swept reservation released). A failed authority signature request cancels the action with a nonce-only transaction over the same nonce, which leaves the receipt behind, settled by the same confirmation.
- Streamflow's auto-claim: one second after a stream's `end_time`, Streamflow's withdrawor empties it into the recipient's token account, even with `automatic_withdrawal` = 0. Anyone calls `sync_sol_stream(position_id, anchor_tx, metadata_data)` on a vault stream; one `AccountState` proof of its metadata adds what it shows withdrawn beyond `engine_withdrawn` to the class's swept balance (`get_sol_swept(class_id)`: `balance`, `pending`). A sync is refused while a payout drawing on the stream or its release is unsettled, and the swept balance is paid with `TransferChecked` alone.
- Refunds happen only when nothing was signed (a proof that failed) or a signed transaction is proven not executed; a signature request never refunds. Unreadable responses are completed by `submit_base_signature` / `submit_sol_signature`; every `Requested` state has a retry (at once after a failed request, after 600 blocks when a callback never ran: `retry_base_signature`, `retry_sol_payout`, re-registration); `resign_sol_gas` completes a missing fee-payer signature.
- Every custody action in flight (a payout not yet final, a deposit registration not yet resolved, a `mt_transfer_call` not yet resolved) holds the account it may credit, which cannot withdraw its storage deposit meanwhile. Callers attach the storage of every record they create (0.025 NEAR per payout record, 0.015 NEAR per deposit attribution, registration or Base cash registration), and the engine keeps 0.5 NEAR free before issuing an MPC request.

## Tests

- `cargo test --workspace`: unit and property tests of the pure modules, contract tests on the near-sdk mocked VM (`src/tests`), the recorded live vectors (`tests/vectors`: clearing, unlock, Sablier `streamedAmountOf` triples, ForeignTx round trips, MPC signatures, web3.js messages).
- `ROSE_SANDBOX=1 cargo test -p rose-engine --test <sandbox_lifecycle | sandbox_recorded | sandbox_staging> -- --test-threads=1`, one suite at a time: NEAR sandbox integration tests with the real engine wasm and the signing `mock-mpc` (every stored signature verified against the bootstrapped keys), the two-phase Solana payout and redeem settled on receipts, a synced Streamflow withdrawal paid from the swept balance, and replays of real staging transactions with their gas (spec 10); see `docs/verification.md`.
- `forge test` (from the repo root): RoseVault and the demo contracts, including fork tests against the live Sablier Lockup.
